04 · Errors & recovery

Keep one failure from taking down the whole experience.

An Observable error ends that stream. Where you catch the error determines whether future user actions can still work.

In plain language

An error is an ending — unless you handle it.

Catch an error around a long-lived stream and that whole stream may stop. Catch it inside one request instead, and the outer stream can keep listening for the next action.

Real-world example

A search box that survives

If one search request fails, the user should still be able to type another query and try again.

Lab 1 · Where to catch

Compare catchError placement

Every third request fails. Keep searching after the failure and see which stream is still listening.

@for (lane of lanes; track lane.name) {

{{ lane.name }} {{ lane.hint }}

Listener: {{ lane.alive() ? 'ready for another search' : 'stopped after the error' }}

}

Rule of thumb

For user-triggered requests, put catchError inside the flattening operator. That handles one request’s failure without replacing or ending the outer click stream.

Lab 2 · Retry carefully

Give a flaky request another chance

This example fails twice and succeeds on attempt three. The delay grows each time: 500 ms, then 1 second.

Attempts made: {{ attempts() }}

Retries help with temporary network hiccups, but use a limit and a delay so a persistent failure does not create a request storm.

Lab 3 · Show errors as UI state

Give the screen a useful state for every outcome

Instead of letting the request error escape, turn it into a state the interface can explain and recover from.

@let result = state(); @if (result.status === 'idle') {

Ready when you are. Press Load data.

} @else if (result.status === 'loading') {

Getting your data…

} @else if (result.status === 'success') {

All set — received {{ result.data }}.

} @else if (result.status === 'error') {

That didn’t work: {{ result.message }}

}

What the user sees

Loading, success, and error are all ordinary states the UI can render. A clear message and a retry action are much friendlier than a blank screen.
